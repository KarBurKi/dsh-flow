# 设计取舍

## 一、为什么不复用 theater 的投递

需求写得很清楚：dsh-flow 和 dsh-theater 无关。所以投递是独立实现的一份——同样的机制（`agent.steer` + 监听 `session/event` 等 `turn/end`），但不 import、不共用数据文件。

代价：投递这套东西两处维护，修一处另一处也得看。收益：剧场插件可以删、可以换、可以不被流程牵制。

如果以后又出现第三第四个需要递话的插件，应该把它抽成一个共享包，而不是继续复制——但现在只有两个，复制一份的代价比多一层依赖小。

## 二、为什么验收写在卡里，不新增状态

状态只留 `pending → processing → done`，和工作室的约定一致。验收是**事件**不是状态：它写进卡里的「## 验收」段，谁都能读、能追溯，不用给状态机加一格。

代价：`flow_run` 得自己判断「验收过没有、过没过」。所以它看的是**最后一段验收**的结论（`结论：通过` / `不通过`），不是「有没有验收段」——不通过后开发重做，卡里会留两段验收，只看「有没有」会把不通过当成通过。

## 三、为什么投递失败不清卡

`flow_start` / `flow_dispatch` 里，投递失败（超时、对方不在）**不删卡、不回滚状态**。

理由：卡是正本，投递只是敲门。门没敲开不等于事情没发生——统筹可以自己去看卡，或者重投。回滚会让「文件已经写好又消失」，比留着更乱。

代价：可能出现「卡进来、统筹没被叫醒」的静默状态。所以这些工具的返回值里有 `delivered` 和 `reply`，调用方要自己看。

## 四、超时 ≠ 没送到

和 theater 一样的教训：`theater_say` / `flow` 的投递超时是「它没在时限内回话」，**消息已经送到了**。提示里写明了，别重发——重发就是发两遍。

## 五、为什么投递正文包代码块

语音播报会跳过代码块。递话是给会话看的，不该被念出来打断主人的语音消息。所以 `deliver()` 统一包三重反引号，调用方不用自己记得。

## 六、归档为什么核对 SHA

「移动」在 Windows 上有几种坏法：跨盘复制后删源、被占用失败、权限不足只复制了一半。核对 SHA-256 才能说「移过去的和原来一样」。不一致时报错并保留文件（在目标位置），不静默吞掉。

## 七、没做的

- 没有定时巡检。各角色开工自己看 `to` 自己的 `pending`。
- 没有并发保护：同一张卡两个人同时 `flow_dispatch` 会互相覆盖，靠约定不靠锁。
- 没有卡片改名 / 移动工具，需要时用文件系统。

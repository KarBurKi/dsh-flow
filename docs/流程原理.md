# 流程原理

这份文档讲**原理**，不讲 DSH 插件怎么写。

dsh-flow 是 DSH 上的一个实现，但流程本身不依赖 DSH：四个角色怎么分工、卡长什么样、状态怎么走、每一步的判据是什么——这些换到飞书、Notion、GitHub Issues、或者自己写的系统里，都能照着复刻。

下面按「为什么 → 是什么 → 怎么走 → 怎么换平台」的顺序写。

---

## 一、这个流程为什么长这样

多会话（或多个人）协作出两个毛病：

**毛病一：自己验自己。** 写代码的人跑通了自测，就说「做完了」。但他验的是「我以为对的地方」，不是「别人会踩的地方」。没有第二个人按判据独立走一遍，边界永远是黑的。

**毛病二：流程活在脑子里。** 派了谁、到哪一步、卡在哪，全散在各人记忆里。换一天、换一个人，就接不上。口头说过的话，第二天就没人认。

所以这个流程只做两件事：

- **把「验收」从「开发环节」里切出来**，交给一个不写这段代码的人，按卡上的判据独立走。
- **把流程从脑子里搬到文件里**：一条活的全部状态，写在它自己的卡上。谁来读都读得懂，不靠传话。

四个角色不是「四个部门」，是四种**边界**。边界清楚，责任才不会糊。

---

## 二、五个抽象

整套流程只有五个东西。平台可以换，这五个抽象不换。

### 1. 角色（role）

| 角色 | 职责 | 硬边界 |
| --- | --- | --- |
| 统筹 | 拆解、建卡、派单、派验收、汇总、归档 | 不自己动手实现；不替别人拍板 |
| 预研 | 提需求、写说明、选型 | 不直接改实现 |
| 开发 | 认领、实现、自测、回执 | **不自验**——自测通过不等于验收通过 |
| 测试 | 独立验收、出报告、报边界 | 不替开发改代码；不接「边改边验」 |

最少两个角色就能跑（开发 + 测试），四个是这套流程的完整形态。**「开发不自验」是整套流程的唯一硬约束**，其余的边界都可以按团队调整。

### 2. 任务卡（card）

一张卡 = 一条活的正本。它是一份文档，不是一条聊天记录。

卡的第一段是机器可读的头部，后面是人写的正文：

```markdown
---
from: 预研          # 谁提的
to: 统筹            # 当前该谁动
type: 任务卡        # 决定归档到哪个子目录
ticket: NA          # 工单号，没有就 NA
status: pending     # pending / processing / done
created: 2026-10-25
---

# 任务卡 · <主题>

## 要求
...要什么、约束是什么...

## 验收标准
...可判定的判据，一条一条写...

## 回执
...执行方填：改了什么、验了什么、版本、推送 SHA...

## 验收
...测试填：结论（通过/不通过）、报告路径、备注...
```

**为什么卡是正本，聊天不是**：聊天是流水，读起来要往回翻；卡是快照，任何时刻打开就知道当前状态和下一步。派单、验收、归档都围着这张卡转，聊天只用来「叫醒」人。

**为什么状态写在卡头，不写在外部系统**：卡和状态放在一起，移动/归档不会脱节；一个文件就是一条活的全部。外部系统（看板、数据库）可以做视图，但正本必须在卡上。

### 3. 状态机

只有三个状态，加一个事件：

```
             派单               验收通过后关闭
  pending ────────► processing ─────────────► done
     ▲                  │
     │                  │ 验收不通过
     └──────────────────┘（投回开发重做，状态留在 processing）
```

- `pending`：卡建好，等统筹派单（或等认领）
- `processing`：已经派出去，有人在干/在验
- `done`：关闭并归档
- **验收是事件，不是状态**：它写成卡里的「## 验收」段，不新增状态。这样状态机只有三条线，谁都能记住；验收的结论、报告、边界都在卡里可追溯。

不通过不退回 `pending`——退回 `pending` 会让人以为「这活还没派过」。留在 `processing`，把「不通过」写进卡，开发重做。

### 4. 投递（dispatch）

投递只做一件事：**叫醒对方，让他去看卡**。

一条投递带三样：

- **谁投的**（哪个角色/会话 id）
- **要什么**（一句话：看哪张卡、干什么）
- **急不急**

投递正文只说「去看哪份文件」，不把卡的内容抄一遍。抄一遍的结果是：两处内容不同步，谁也不知道哪份是真的。

平台映射：DSH 里是会话间直接投消息；飞书是企业群里 @ 人；GitHub 是 issue 里 @ 和 label；自建系统是站内信/通知。

### 5. 归档（archive）

`done` 之后，卡从「在途」目录移到归档目录：

```
在途：任务卡/<YYYYMM>/...
归档：归档/<类型>/<YYYY-MM>/
   例：归档/任务卡/2026-10/任务卡_视频录制插件_..._20261025.md
```

移动前后**核对文件哈希**（SHA-256）。理由：移动在文件系统上有好几种坏法（跨盘复制一半、被占用失败、权限不足），不核对就说「归档好了」是在赌。

平台映射：归档目录在飞书是知识库、在 GitHub 是 milestone + close、在自建系统是 status=archived。

## 三、一条活的完整时序（七拍）

每拍写：谁动、做什么、产出什么、判据是什么、失败了怎么办。

### 第 1 拍 · 预研提需求

- **谁**：预研
- **做什么**：想清楚要什么、为什么现在要，写成卡头的「要求」和「验收标准」
- **产出**：一张 `status: pending` 的卡，`from: 预研`、`to: 统筹`
- **判据**：验收标准是**可判定的**（「能起录、产物能播」而不是「录制功能良好」）
- **失败**：判据写不出来，说明需求还没想清，不往下走
- **动作**：投递给统筹——「新卡，请拆解」

### 第 2 拍 · 统筹建卡、拆解、派单

- **谁**：统筹
- **做什么**：看卡、确认判据可行、决定要几个人干，把卡派给开发
- **产出**：卡状态 `pending → processing`，卡里多一行派单记录（谁、什么时候、什么附言）
- **判据**：卡的 `to` 改成执行者；验收标准没被偷偷放宽
- **失败**：判据不可行/缺前置条件，退回预研，卡退 `pending`
- **动作**：投递给开发——「派单，请认领」

**为什么要记派单行**：一周后回看这张卡，「谁在什么时候接的」是唯一能追溯的东西。聊天记录会沉，卡不会。

### 第 3 拍 · 开发认领、实现、自测、回执

- **谁**：开发
- **做什么**：照卡实现，按判据自测，在卡末写「## 回执」
- **产出**：可运行的成果 + 回执（改了什么 / 验了什么 / 版本 / 提交号）
- **判据**：每一条验收标准都有对应的证据（跑过什么、看到什么）
- **失败**：做不完/卡住，在卡里写清卡在哪，不要静默不动
- **动作**：投递给测试——「实现完了，请独立验收」

**回执不是结论，是证据清单**：写「改了什么、拿什么验的、输出是什么」，不写「已完成、没问题」。后者没有信息量。

### 第 4 拍 · 测试独立验收

- **谁**：测试
- **做什么**：**只看卡的「要求」和「验收标准」**，不看开发回执的结论，按判据从头走一遍
- **产出**：卡里追加「## 验收」段：结论（通过/不通过）、报告路径、备注
- **判据**：每一条验收标准都单独判过；**写清没验的部分**（边界）
- **失败（通过）**：投递给统筹——「验收通过，请归档」
- **失败（不通过）**：投递给开发——「不通过，报告在 X，请重做」，状态留在 `processing`

**独立的意思**：不走开发的走法、不问他「你是不是这么测的」、不复用他的测试脚本。同一个判据，换一种方式再验一遍。他验的是「这个地方」，你验的是「卡上写的这个地方」。

**「没验的部分」必须写**：验收报告里最值钱的一句是「这个我没测」。没有它，读报告的人会以为全都测了。

### 第 5 拍 · 统筹汇总、关闭

- **谁**：统筹
- **做什么**：确认验收结论存在且通过、回执与验收对得上，然后关闭
- **产出**：卡状态 `processing → done`
- **判据**：卡里有验收段且结论为「通过」；没有验收段的不许关闭
- **失败**：缺验收/验收不通过，退回上一拍
- **动作**：归档

### 第 6 拍 · 归档

- **谁**：统筹（或一个定时任务）
- **做什么**：把 `done` 的卡从在途目录移到归档目录
- **产出**：卡在 `归档/<类型>/<YYYY-MM>/` 下
- **判据**：移动前后哈希一致；目标位置不覆盖同名文件
- **失败**：哈希不一致 → 报错并保留文件，人工核对，不静默吞

### 第 7 拍 · 回到起点

归档完成的那一刻，这条活结束了，**同时下一轮开始了**：预研看到缺什么、踩到什么，提下一张卡。这就是「自循环」——不是循环同一件事，是循环同一套动作。

## 四、状态转移表（可直接实现）

| 当前状态 | 事件 | 新状态 | 谁触发 | 副作用 |
| --- | --- | --- | --- | --- |
| （无） | 预研提需求 | `pending` | 预研 | 建卡、投递给统筹 |
| `pending` | 统筹派单 | `processing` | 统筹 | 改 `to`、记派单行、投递给执行者 |
| `processing` | 开发提交回执 | `processing` | 开发 | 追加回执段、投递给测试 |
| `processing` | 验收通过 | `processing` | 测试 | 追加验收段（通过）、投递给统筹 |
| `processing` | 验收不通过 | `processing` | 测试 | 追加验收段（不通过）、投递给开发 |
| `processing` | 统筹关闭（有通过的验收） | `done` | 统筹 | 移到归档目录、核对哈希 |
| `processing` | 统筹关闭（无验收） | 拒绝 | 统筹 | 报错「没有验收结论」 |
| `done` | 再关闭 | 拒绝 | — | 报错「已经 done」 |

规则只有三条：

1. **状态只能前进，不能后退**（不通过不退 `pending`）
2. **关闭必须有通过的验收**（没有验收的 `done` 是耍赖）
3. **`done` 之后卡不再改**（要改就开新卡）

## 五、换平台怎么复刻

### 5.1 抽象映射

| 抽象 | DSH 实现 | 飞书 / 钉钉 | GitHub | Notion | 自建系统 |
| --- | --- | --- | --- | --- | --- |
| 角色 | 会话 id | 群成员 / 机器人 | 人 + label | 成员 | user 表 |
| 任务卡 | 文档区里的 .md | 云文档 | Issue | 页面 | tasks 表 + 正文 |
| 卡头状态 | YAML frontmatter | 文档属性 / 标签 | label（`status:pending`） | 页面属性 | `status` 字段 |
| 派单 | 会话投递 | @ 人 + 私信 | assignee + comment | @ mention | 站内信 |
| 验收事件 | 卡里的「## 验收」段 | 文档里的表格 | comment + label | 页面区块 | `verify` 子表 |
| 归档 | 移动文件 | 移到归档空间 | close + milestone | 移入归档库 | 改 status |
| 哈希核对 | sha256 | 不适用（云端） | 不适用 | 不适用 | 移动前后 checksum |

### 5.2 最小实现清单

不管在哪个平台，下面这些缺一不可：

**必须有**

1. 一份卡 = 一条活，有唯一 id（文件名或数据库主键）
2. 卡头有机器可读的 `status`（三态）
3. 卡里能追加内容（回执段、验收段），追加后原内容不变
4. 能「叫醒」下一个角色（通知/投递/@）
5. 有「在途」和「归档」两个位置，`done` 后移过去

**强烈建议**

6. 验收结论和「没验的部分」写进卡（不是只写在聊天里）
7. 归档前做一致性校验（哈希或逐字段比对）
8. 关闭操作校验「有通过的验收」

**可选**

9. 一键推进（读状态自动走下一步）
10. 定时巡检（找超过 N 天没动的卡）——本流程没实现，靠各角色自己看

### 5.3 平台特有的坑

- **状态放在云端系统里**：卡正文和系统状态分离，两边会打架。解决办法：以卡正文为正本，系统状态只做视图，冲突时以卡改写。
- **追加内容会改历史**：有些平台的文档不支持「只追加不改前面」。退一步：验收写在新评论/新页面里，并在卡头放一个 `verify_ref` 指向它。
- **通知不可靠**：投递失败（对方没在线）不等于事情没发生。所以投递工具必须返回「送到了没有」，并且**不因为超时回滚卡**——卡是正本，敲门失败是敲门的事。
- **没有 SHA**：云端文件没有本地哈希。退一步：归档前比对「字段数、行数、字数」或做一次内容 diff，至少要能发现「只移了一半」。

### 5.4 复刻成功的判据

照着上面做完，怎么知道自己复刻对了？

1. **走一遍完整闭环**：提卡 → 派单 → 回执 → 独立验收 → 关闭 → 归档，每步都在卡上留下痕迹。
2. **验一次拒绝路径**：没验收就要关闭 → 被拒绝；`done` 后再关闭 → 被拒绝；验收不通过 → 卡在 `processing`。
3. **验一次重启**：把流程放一天再回来看，打开卡就知道下一步该谁动——不用问任何人。
4. **验一次「不同步」**：卡的状态和聊天里说的不一致时，以卡为准，且卡是对的。

四条都过，就是复刻成功了。

## 六、不变量（换平台也不能改的）

1. **卡是正本**：状态、派单记录、验收结论都在卡上；聊天和看板都是视图。
2. **开发不自验**：做的人不判自己。这条松了整个流程就没有意义了。
3. **验收写结论也写边界**：只说「通过」的验收不算验收。
4. **状态只前进**：不通过不退 `pending`，留在 `processing`。
5. **关闭要有通过的验收**：没有验收的 `done` 是耍赖。
6. **投递超时 ≠ 没送到**：卡是正本，投递只是敲门；超时后先看卡，别重发。
7. **归档要核对**：移过去的和原来一致才算归档完成。

## 七、和「一键」的关系

一键（`flow_run`）只是**把七拍的顺序写进代码，替调用者重复执行**。它不负责：

- 改实现（那是开发的事）
- 编验收结论（那是测试的事，而且编出来的结论没有意义）
- 替人拍板（那是统筹的事）

所以一键到底还是会在「等验收结论写进卡」这一步停住——因为它不能替测试做判断。**这是设计，不是缺陷。**

平台无关的结论：**自动化能省的是「照着卡走」的重复劳动，省不了「判断」本身。** 任何声称能全自动闭环的工具，都在偷偷替你判断。
